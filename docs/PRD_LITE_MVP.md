# HYNAK 巴西经销商订单、库存与回款系统

## 轻量版 MVP 产品需求文档（Codex 快速开发版）

> 版本：V0.1｜日期：2026-10-28  
> 项目目标：**先上线能真实使用的业务工具，之后逐步扩展**。本文件取代此前35KB《第一阶段MVP PRD》的**近期开发范围**；未覆盖的已确认需求保留在未来版本，不允许自动扩展到本期。

## 1. 业务目标与上线成功标准

目前 HYNAK 核心问题不是缺少复杂 ERP，而是订单确认、真实库存和货款回收缺少统一台账。

本版必须解决：

1. **在线下单**：经销商账号自行下单；HYNAK 销售人员可为经销商代拟订单，发送网页链接，让经销商在手机上查看并点击确认。
2. **库存透明**：HYNAK 管理多个仓库（一级/二级）以及经销商寄售库存；出入库可追踪，系统知道哪些车已售、已发、仍在仓库或寄售点。
3. **每单收款状态**：准确区分应收、经销商声称已付、财务核实到账、尚欠及逾期。
4. **回款跟进**：按经销商、责任销售员查看欠款；提供一键打开 WhatsApp 并填入催款文本（员工手动发送）。
5. **简单佣金**：按订单责任销售员统计销售及符合条件的佣金，财务手动确认结算，不做复杂奖金引擎。

**验收标准**：一张真实订单从创建/经销商确认、HYNAK 审核，到库存出库、应收产生、收款核实、逾期追踪、佣金候选计算的全流程跑通；数额和库存可独立复核。

## 4. 订单核心流程（最重要）

### 4.1 两条下单路径

#### 路径 A：经销商自行下单

1. 经销商登录网页，查看车型、**标准批发价**、有货/无货标识，选择数量（无货可提交待补货订单）。
2. 提交订单 → `待 HYNAK 审核`。系统不得立即生成正式发货单，也不得把未审核订单算入正式应收。
3. HYNAK 管理员/授权主管审核并确认最终价格、Demo 或10+1优惠、订单责任销售、付款到期日。
4. **HYNAK 审核通过，订单直接生效，无需经销商再次确认**（延续此前确定的第141题规则）；经销商页面可查看最终金额。

#### 路径 B：销售人员代下单 + 链接让经销商确认（本次新核心需求）

1. 销售选择经销商、车型/数量、促销方案，生成**待确认报价订单**。
2. 管理员/授权主管先确认最终价格与付款条件，并锁定本次报价快照。
3. 销售点击 **“复制确认链接”**，通过 WhatsApp 发给经销商。
4. 经销商在手机上打开链接，看到 HYNAK 品牌、订单号、车型、数量、标准价/最终成交价、优惠、总价、付款条件、有效期，点击 **“确认订单”** 或 **“拒绝”**。不得自动确认。
5. 经销商点击确认后订单**立即生效**，不需重复内部审核，因为发链接前已审核价格；拒绝则标记拒绝。
6. 如 HYNAK 更改已发链接的车型、数量、金额或付款条件，**旧链接失效，必须生成新链接让经销商重新确认**。不能在客户确认后悄悄修改价格。

**确认链接最小安全标准：** 使用高熵随机 token（例如32字节以上，数据库只保存哈希），有有效期（默认7天，可撤销）、一次性终态确认、防重复提交；访问链接只提供该订单必要信息，绝不暴露其他经销商或银行账户内部资料。确认时记录时间、订单版本及确认动作，IP/设备信息可作为辅助手段但不代表法律意义的电子签章。**云端公开链接必须使用 HTTPS**。本地单机时可演示同机确认；**要让远程经销商收到并打开链接，必须先部署一个可互联网访问的 HTTPS 测试/正式站点**。

### 4.2 订单状态与应收

订单：`DRAFT`（草稿）→ `WAITING_INTERNAL_REVIEW` / `WAITING_DEALER_CONFIRMATION` → `CONFIRMED`（生效）→ `PARTIALLY_SHIPPED / SHIPPED` → `CLOSED`；另有 `REJECTED / CANCELED / EXPIRED`。

付款状态独立：`UNPAID / PARTIAL / PAID / OVERDUE`。发货状态必须独立于付款状态，不允许一个字段包办所有含义。

- **普通批发订单**：生效后生成经销商应收记录。经销商已确认但尚未出库时，仍保留待发状态。
- **锁货**：订单生效后有货部分可锁定库存，默认72自然小时；到期前如财务未确认任何到账，自动/在服务启动时执行释放锁货，订单保留但显示“待重新分配库存”；如已有**任意金额的真实核实到账**则不自动释放，由管理员处理。只有上传截图不算到账。无货数量显示待补，不凭空锁货。
- 默认整单出货；紧急部分出货由管理员允许。**创建出库单时扣库存**；记录是否实际提货，未提货撤销可回补，已提货只能凭实际退回冲回。
- 退款/撤单：首版管理员通过记录一笔**可审计的人工调整/冲销**处理，不做自动退款网关。

### 4.3 Demo 与 10+1

- SKU 标准批发价保存在系统中，以巴西雷亚尔（BRL）计价。
- **Demo 单价=该车型标准批发价×80%**，而不是经销商专属价×80%。
- **10+1**：同款车型购买10台付费车赠1台；购买25台赠2台；赠车作为 R$0 的独立订单行，实际出库要扣库存。
- **Demo 与10+1不能在同一订单叠加**；审核人员可以特殊改价但必须写原因和操作日志。
- 首版在赠车缺货时显示“待补赠品”，财务应收不增加；不开发复杂自动赠车排队/跨仓分配引擎。特殊70/30单的赠品须等全额到账后才能出库。

## 5. 库存管理：少页面但数据正确

### 5.1 基本对象

- 商品：车型 SKU、名称、标准批发价、是否在售；型号如 R6 mini / R6 Pro / R6 Max、MT2 / MT2 Pro、S1 / S1 Plus / GT1 dual 等，可增减。
- 库存地点：一级仓、二级仓，以及**经销商寄售位置**。由管理员新增地点，不硬编码仓库名。
- 库存动作：`期初`、`入库`、`出库`、`调拨`、`寄售发出`、`寄售售出`、`寄售退回`、`经核准的调整`。
- 所有库存变化必须写入**不可直接编辑的流水**，含关联订单、仓库、SKU、数量、操作人、时间、原因；余额由流水计算/维护，不允许直接修改余额覆盖历史。

### 5.2 业务规则

- 调拨一级仓→二级仓，不产生销售和应收，两仓库存一减一加。必要时可由管理员校正历史差异，但保留调整流水。
- 货送至经销商**寄售**位置，仍属于 HYNAK 存货；**寄售交车不产生销售应收**。
- 经销商上报寄售已售台数，HYNAK 确认后降低该经销商寄售库存、生成销售应收；确认必须幂等，不得重复扣库/开应收。
- **负库存只有 HYNAK 管理员可操作**，必须填写原因；其他角色出库导致负数时后端直接拒绝。负库存是账面登记例外，不代表实际交付。
- 首版在出库界面提供车架号/SN 输入与异常标记；如果旧数据缺号，不得虚构号码。复杂逐台生命周期追踪后置。
- 经销商只看到车型是否可预订、自己的寄售数量；看不到 HYNAK 全部库存或仓库地址。

## 6. 应收、收款确认与催收（本次核心）

### 6.1 必须分清四种金额

| 指标 | 定义 |
|---|---|
| 应收（Receivable） | 经 HYNAK 确认生效的批发订单金额 + 已确认寄售售出形成的应收 − 有效冲销 |
| 付款申报（Payment claim） | 经销商声称已付款、上传银行截图，**尚未银行核实** |
| 已收（Verified receipt） | 财务确认实际到账的金额、日期、收款账户及银行参考号 |
| 未收（Outstanding） | 应收 − 已被分配至订单的有效已收款 − 有效抵扣；不得为负 |

金额用**整数分或 Decimal**，不能使用二进制浮点运算。实际收款账户及其别名统一管理；历史 `TF`、`xt` 为**同一真实收款账户**，`xiaolu`、`卢` 在财务确认前不得合并。

### 6.2 操作流程

1. 订单生效自动产生应收。财务可设置或调整到期日并留下原因；寄售销售在 HYNAK 确认后才应收。
2. 经销商在订单页上传付款截图，填写申报金额/时间/交易参考；系统显示“待财务确认”。
3. 财务核对银行后确认**实际到账金额、日期和真实收款账户**。确认操作不可重复入账，同一银行交易参考号重复需阻止/标记。
4. 财务将真实到账分配至该经销商一笔或多笔订单。**超额到账**保留为经销商预存款，不得被误算成负欠款。
5. 经销商看自己的订单应付/已收/未付；销售看负责客户的欠款，财务/管理员看全量。
6. 催收列表按**逾期天数、欠款金额、经销商、销售负责人**筛选；支持填写本次催收备注、下次跟进日期及跟进人。
7. 点击“WhatsApp 催款”，使用其手机号打开聊天页面并预填对应语言的订单号/欠款/到期日信息，由员工人工点击发送。**没有官方 API，不得声明已自动发出。**

### 6.3 必须有的首页指标

- 待确认订单数、今日/本月已生效订单额；
- 各仓库存（按 SKU）、寄售库存；
- 全部应收、银行核实已收、尚欠、逾期金额；
- **欠款金额最高的经销商**及催收待办；
- 按销售人员查看负责经销商的应收/已收/欠款；
- 明确区分“客户上传截图”和“财务确认到账”。

## 7. 简易佣金

佣金只做**运营汇总和手工结算**，不是完整工资/绩效系统。

- 每笔订单指定**唯一责任销售员**（多人跟进可备注，佣金仅归属一个人）。
- 每名销售员设置**一个默认佣金比例**（例如3%仅为样例，不预设真实比例）；管理员可以对特定订单做经批准的例外调整。
- **只有整笔订单全部实际出库交付、车辆销售款财务核实全部收到，并由销售主管/管理员确认后**，才列为“可结算佣金”；货运费、赠车和配件不计提。分期、仅收首付款的订单不提前正式结算。
- 本版公式：`可结算佣金 = 已确认的车辆实际成交净额 × 经批准的佣金比例`，按 BRL 两位小数舍入。保留计算基数、比例、负责人、审核人和结算状态快照。
- 简化状态：`未满足条件 / 待审核 / 可结算 / 已结算`；按月汇总，财务手动记录付款日期、金额和备注。
- 退款、跨期调比例、跨产品差异比例等复杂情形先由授权人员**记负数调整或人工复核**，不得自动按错误规则支付；原完整 PRD 中按收款时间分段的复杂比例和自动追佣留第二阶段。

## 9. 历史 Excel：快速上线的数据策略

历史源文件包含9张工作表：寄售交易数据、现付交易数据、二级仓库库存管理、一级仓库库存管理、巴西电动自行车支出、配件表、配件销售、盘点记录、余额检查。

**本版不开发九张工作表全部逐行自动重构为完整交易账本的复杂迁移器。** 采用**确定切换基准日 + 核实期初快照**的可控快速导入方案：

1. 由用户/仓库/财务确认一个切换日（cutover date），导出或整理该时点的：`车型标准价`、`经销商及负责销售`、`分仓期初库存`、`经销商寄售期初库存`、`尚未结清的应收单据`、`经确认的客户预存款`。
2. Codex 提供上述6类**Excel 模板或固定列映射**、预览、错误校验、批次导入、记录来源及重复导入检查；对未核实行标注 `待核实`，不进入正式余额。
3. 切换日前历史**已收款**仅可用于说明历史欠款余额的形成；没有银行核实依据不得生成“本期银行实收”。期初未收可以作为**明确注明期初来源的应收余额/账单**，避免历史销售再次计入本期业绩。
4. 保留原始9表文件作为**只读来源附件/备份**，第二阶段再做逐行历史还原、复杂导入核对；不要扔掉原表。
5. `TF` 和 `xt` 指向同一收款账户；Demo应收按标准价×80%核算，但**不可由折扣倒推已收款**；免费售后换车/展示样车不得被自动算成真实销售应收。
6. 各核心模块可按经销商、仓库、车型、日期、销售负责人筛选导出 XLSX，导出必须受后端权限限制。

> 这是一项刻意的范围缩减，目的是让系统先替代日常 Excel 记录。若要求9张历史表逐笔对账、全部历史应收和收款自动重建，则开发周期明显变长，需要另列迁移项目，不能阻塞首版下单和催收上线。

## 10. 技术建议：单体优先，避免过度设计

为了最快上线，建议 **Python FastAPI + SQLAlchemy + Jinja2/HTMX（或等效轻量前端）+ SQLite（本地）/ PostgreSQL（云端）**，前端输出普通 HTML/CSS/JS 页面，无须先搭建庞大 React 多应用架构。Codex 可以选择等效技术，但必须在开始编码前说明理由。

- 单仓库、单体后端、单数据库源；关键交易都在后端进行，付款金额用 Decimal/整数分。
- 数据表初期优先包括：`users`, `dealers`, `products`, `warehouses`, `orders`, `order_lines`, `order_confirmation_tokens`, `stock_ledger`, `stock_reservations`, `consignment_records`, `receivables`, `payment_claims`, `bank_receipts`, `payment_allocations`, `dealer_credit`, `collection_followups`, `commission_records`, `import_batches`, `audit_logs`；按实际设计可合并或扩展。
- 附件存储在本地私有目录/云端私有对象存储，不能无鉴权公开访问付款截图。
- macOS、Windows 分别提供**双击启动脚本**：`start-mac.command`、`start-windows.bat`，首次初始化可有简单安装向导/脚本；日常无需输入终端命令。不要求第一版制作正式 `.dmg` / `.exe` 安装器。
- 本地 `127.0.0.1` 运行，单机测试；云端 HTTPS 域名上线后远程经销商才能操作订单和确认链接。环境切换使用配置文件和可迁移数据库 schema，禁止在代码中写死本地 URL。
- SQLite 数据库和附件不能放入会被覆盖的程序目录；每日至少一次基础自动备份，能在隔离环境恢复；云端上线须部署 HTTPS、最小权限、备份及错误日志。
- 出错不能静默成功；对于订单确认、入出库、财务到账，必须有**数据库事务 + 幂等校验 + 审计日志**。
- 不得把真实银行账号、Excel 全量文件、客户信息、密码和密钥提交至公共 Git 仓库。

## 11. 建议开发顺序与粗略排期

> 排期假设：1名有经验的全栈开发人员，利用 Codex 辅助；业务决策和验收可及时完成。**时间是估算，不是承诺**。

| 里程碑 | 重点 | 估算工作日 | 交付判断 |
|---|---|---:|---|
| W1 底座+订单 | 登录权限、商品、经销商、双路径下单、确认链接、审核/价格 | 4–6 | 真实订单可以提交、由客户确认、生效 |
| W2 库存+应收 | 仓库、库存流水/寄售、订单应收、付款截图/银行核实 | 4–6 | 一笔订单库存和欠款变化可追溯 |
| W3 催收+佣金+导入 | 欠款面板、催收记录、简易佣金、期初模板导入、导出 | 3–5 | 可以实际开展销售/催收业务 |
| W4 验收+上线 | Mac/Win 启动、数据核对、权限测试、备份、HTTPS 云端发布 | 3–7 | 经销商在手机上确认真实链接，数据持续保存 |

**目标：本地可用约2–4周；含云端试运营约3–6周**。真实历史数据差异复杂、业务规则频繁变更或需生产级多端兼容时会更长。比原来约10–16周的完整版本大幅精简。第一版无需5个 Codex 窗口同时开发，**1个主 Codex + 1个测试/复核 Codex**更合适，减少接口协调成本。

## 12. 最低验收用例（不可省略）

| 编号 | 用例 | 合格结果 |
|---|---|---|
| U01 | 经销商自行提交订单 | 待审核；HYNAK 审核后生效，不需要经销商二次确认 |
| U02 | 销售代拟订单，生成链接 | 价格先内部审核；客户可用手机查看并手动确认，订单后生效 |
| U03 | 代拟单的旧确认链接被撤销、过期、重复点击或订单改价 | 不会重复生效；改价须新链接确认 |
| U04 | Demo 标准批发价 R$5,800 | 成交价 R$4,640，不能叠加10+1 |
| U05 | 同款25台10+1 | 赠2台R$0，出库占用真实数量 |
| U06 | 经销商上传 R$5,000 付款截图 | 正式已收款不变；仅财务核实到账后改变 |
| U07 | 银行核实到账 R$3,000 并分配到两订单 | 实收仅计算一次，各单欠款准确，不能超额分配 |
| U08 | 一个订单到期未付 | 出现在逾期列表，正确计算逾期天数，销售可记催收跟进 |
| U09 | WhatsApp 催收按钮 | 打开正确号码和消息草稿，**没有声称自动发送成功** |
| U10 | 普通仓管从5台库存出库10台 | 被拒绝；管理员给出原因后可记录负5异常库存 |
| U11 | 调拨5台到二级仓 | 两仓一减一加，总库存不变，不产生销售应收 |
| U12 | 寄售10台，确认售出3台 | 剩7台寄售；只针对确认的3台形成应收，重复确认不双扣 |
| U13 | 某订单仅付部分车款或尚未全数交付 | 佣金不进入可结算；全付、全交付、审核后才可结算 |
| U14 | 新系统从已核实期初余额导入，再重复导入同批次 | 不重复加库存、应收或预存款；待核实行不影响正式余额 |
| U15 | 经销商甲尝试看经销商乙订单和付款截图 | 后端拒绝；不得通过导出、确认链接越权访问 |

| U17 | 云端 HTTPS 测试确认链接 | 外地经销商可在手机上正常确认，订单与库存/应收同步正确 |

**硬约束：** 任何已核实金额（应收、实收、未收）的总额和订单明细差异必须为 **R$0.00**；仓库已核实期初与每笔出入库数量可追溯。不得为了“通过验收”虚构银行到账或覆盖原始记录。
